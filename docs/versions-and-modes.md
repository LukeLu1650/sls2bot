首次跑局锁定上游研究环境。新模式从独立游戏构建接入，先验证实际规则，再复用骨头人策略。表中“待适配”是开发状态。

| 标准模式跨版本 | 官方主线 v0.111.1 改为 12 位种子，调整 RNG、骨头人卡牌和战斗结算 | 作为迁移案例，重新生成种子面板并验证回放 |

## 每次更新怎样接入

1. **建立新环境快照。** 为候选构建新开研究目录，记录平台、游戏版本与分支、程序集和资源哈希、适配器 Git 提交、解锁状态及语言。保留旧适配器、种子、基线输出和模型，便于并行复查。
2. **检查接口与规则差异。** 对照官方更新记录，盘点卡牌、遗物、敌人意图、合法动作、决策点、词表、种子算法和终局判定。以稳定的游戏内容 ID 对齐词表。ID 顺序或含义变化时生成映射，新增行独立初始化；未知的可交互动作应留下现场样本供适配，避免当作跳过。将旧的原始轨迹、重启快照、新采样缓冲区按构建分开存储。
3. **验证宿主。** 以新构建的真实客户端作对照，固定本构建的种子和动作序列，在战斗、奖励、购物、事件、跨幕、死亡及胜利处比较玩家可见状态、合法动作和下一次决策。骨头人另测 Osty 与灾厄结算。出现差异即保存最早分歧前后的状态。旧版十位和新版十二位种子各自采样；同一个字符串没有跨版本等价保证。
4. **验证模型。** 检查点附带游戏构建、模式、难度、角色、网络形状、观测/动作协议、词表哈希、权重哈希和训练步数。字段一致才直接加载。仅数值平衡变化时先零样本评测；特征或词表变化时明确迁移并重新导出，使用新版真实轨迹核对。
5. **发布一套可复测的结果。** 每个版本和模式分别存储训练、开发和封存种子及其哈希。旧策略和候选策略都在同一个新构建、同一组种子上跑，记录引擎错误和差异；同时保留旧构建自己的基线。若更新导致退化，可以重新选择旧的游戏快照、适配器、词表和模型组合。

每轮保存一份运行记录，至少包括 `game_build, platform, adapter_commit, mode, difficulty, character, unlocks, seed_protocol, panel_sha256, observation_schema, action_schema, vocab_sha256, model_sha256, initialization, new_decisions, replayed_decisions, wins, games, errors`。评测记录还需注明隐藏信息过滤、规则自动处理项和推理方式。大文件按 `runs/<构建>/<模式>/<角色>/<实验编号>/` 分类，发布结果时附记录和逐局摘要。

## 两个新模式分别怎么训练

| | 急速模式 Blitz | 恐惧模式 Dread |
| --- | --- | --- |
| 已知规则 | 官方介绍为压缩流程、强调构筑；移除地图，改动商店，金币失去常规用途。5 个进阶等级跨角色共享 | 全部进阶修正生效；Boss 更强，并强化本幕敌人，诅咒随推进累积。官方公告中的解锁条件包括所有角色达到 A10 |
| 环境与观测 | 模式 ID、当前阶段、构筑选项、专属商店和实际可选交易。将地图标记为“不适用”，由游戏列出合法动作 | 模式 ID、当前幕、可见 Boss 强化、敌人状态、诅咒与骨头人资源。按照当前构建在实机显示的时点暴露信息 |
| 训练目标 | 对照标准模式骨头人策略的迁移效果；以通关为主奖励，按实际阶段调节奖励尺度。分进阶报告选牌、交易、阶段通过和胜率 | 先以标准模式骨头人 checkpoint 为对照，记录各幕及 Boss 前死亡分布，再在训练种子上重练高失败场景。主要成绩来自完整新局 |
| 首批回归场景 | 开局无地图、特殊商店、奖励选择、阶段切换和终局。从头跑完一局，检查策略是否等待普通地图或金币交易 | 跨幕替换 Boss 强化、普通敌人获得强化、诅咒累积、Osty 承伤和灾厄击杀、最终胜负。与同构建实机核对结算顺序 |

首次接入时，每种模式各自从同一个标准模式 checkpoint 初始化一个副本，使用独立的优化器、训练预算与评测面板。比较“直接迁移”和“本模式微调”后，再决定是否训练带 `mode` 标识的共享网络；共享版本须在三个模式各自的固定测试集上报告成绩。急速的五档进阶与恐惧的全修正规则应在指标中保留各自含义。[Mega Crit 模式说明](https://store.steampowered.com/news/app/2868840/view/708914333639245837)
